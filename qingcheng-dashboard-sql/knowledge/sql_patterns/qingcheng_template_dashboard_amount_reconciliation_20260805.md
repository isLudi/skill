## 3. 根因定位

### 3.1 模板保留试听订单，看板 SQL 排除了试听订单

模板原始 SQL `resources/raw_sql/qingcheng_channel_order_detail_raw_20260627.sql` 的 `gmv` 层限定业绩二级部门为青橙，但没有排除 `clazz_name like '%试听%'` 的流水。

当前三个完成度数据集的 `service_base0` 明确使用：

```sql
and coalesce(s.clazz_name, '') not like '%试听%'
```

诊断查询对全部差异键重新计算后，模板与看板的差额逐笔等于被排除试听流水的 `income_amount / refund_amount`：

- 非 H 课程损失：所有差异键收入、退款均为 `0`；
- 渠道 `ld` 重复放大：所有差异键重复行数为 `0`，额外收入、退款均为 `0`；
- 试听流水：10 个差异键均可由试听收入或试听退款完全解释。

因此，本次五期核对的直接原因是：**模板把试听订单纳入金额，看板按当前业务定义排除了试听订单。**

### 3.2 不是 finance 源表重复行导致的当前金额差异

`finance_dw.app_finance_performance_extend_details_hf` 的不完整投影键不能代表当前调课调班明细的唯一粒度；当前三份完成度 SQL 保留独立 finance 明细并按真实业务粒度聚合，再用 `order_number + employee_email_name` 判断 service 是否已覆盖链路。但当前看板的 `income_all/refund_all` 仍由 service 明细直接汇总：

```text
income_all = sum(service income_amount / 100)
refund_all = sum(service refund_amount / 100)
```

finance 不参与这两个全部收入/全部退款字段的正常金额求和。当前五期、同一员工范围的诊断也未发现由渠道明细 join 造成的重复放大。因此，**不能通过修改 finance 源表来解决这组看板与模板的差异**。finance 明细粒度风险仍需在各补充 SQL 中显式处理：不能用不完整投影键吞掉独立行，也不能未经真实粒度聚合直接 join；影响范围主要是 legacy `income/refund`、调课调班补充链路和退 4/点睛退 2 规则字段。

## 4. 当前看板金额公式

当前线上数据集为：

- 个人：model `2769`，`resources/raw_sql/data_center_qingcheng_2769.sql`；
- 团队期：model `2680`，`resources/raw_sql/data_center_qingcheng_2680.sql`；
- 团队月：model `2677`，`resources/raw_sql/data_center_qingcheng_2677.sql`。

金额字段的业务公式为：

```text
班课营收 / 团队营收金额 = sum(income_all)
班课退费 / 团队退费金额 = sum(refund_all)
班课净收 / 团队净金额 = sum(income_all) - sum(refund_all)
```

这三个字段不剔除调课调班，也不把退 4/点睛退 2 规则混入全部退款；`transfer_in_amount/transfer_out_amount` 继续用于内部调课识别，`ord/re_ke` 继续用于退 4、点睛退 2 规则。

折算字段保持原业务含义，不用 `income_all/refund_all` 直接替换：

```text
个人折算后产出
= sum(n_H_promit_4) * 0.5
  + (sum(H_promit_4) - sum(Y_promit_4))

团队折算净收款-退4
= sum(n_H_promit_4) * 0.5 + sum(H_promit_4)
```

即：全部收入/全部退款用于看板金额展示；折算产出仍按原有 H/非 H、退 4、点睛退 2 和个人一对一扣除规则计算。

## 5. 与模板对齐建议

若要求模板取数与当前看板业务含义一致，推荐在模板 `gmv` 源查询中增加：

```sql
and coalesce(clazz_name, '') not like '%试听%'
```

这样可以保留当前看板“排除试听”的业务含义，同时使模板与两个看板在本次验证范围内逐分一致。若反过来删除看板的试听过滤，虽然可以向当前模板靠拢，但会改变“班课营收/退费为非试听正常订单金额”的既有业务含义，不建议直接采用。

本次没有修改线上模板或看板；只更新了本地 `qingcheng-dashboard-sql` 的 canonical SQL 与知识文档。模板精确名称未在当前“我的模板-我创建的”列表中检索到，本次比较采用 Skill 中保留的模板原始 SQL，并补齐 USQL 必需的当前青橙课程范围过滤；因此若模板线上版本另有未保留的筛选条件，应以模板回读 SQL 做最终复核。

## 7. 2026-08-07 调课调班行级回归与三模型上线

### 7.1 根因与修复

20260803期 `张地43` 的专项排查发现，旧版 `order_attr` 按订单和顾问取 `max(transfer_in_amount/transfer_out_amount)`，再将订单级标记回灌到同订单所有 service 明细；该订单约 `12,000` 元正常支付行没有原始 transfer 标记，却被旧规则当作内部流水排除。于是 `income_all=19,800`，但 legacy `income` 和折算后产出只剩 `7,800`。

本次三份 canonical SQL 统一改为：

- `order_attr` 只聚合原始支付时间；
- `service_base0` 在当前明细行识别 transfer 并传递到 `t4`；
- finance 仅在 service 缺失且当前行确为实际退款、变更金额非 0 时补充识别，不按订单整体剔除；
- `finance_dw.app_finance_performance_extend_details_hf` 在当前三份完成度 SQL 中保留独立明细并按真实输出粒度聚合，`income_all/refund_all` 仍由 service 主事实汇总，不受 finance 补充路径影响。

行级回归查询 `1534542940` 显示 `张地43` 修复后 `income=19,800`、`H_promit_4=19,800`、折算后产出 `19,800`。团队期聚合查询 `1534547907` 返回 `output_rows=330`、`income_all=26,961,943.26`、`refund_all=3,507,394.74`、折算后产出 `23,009,158.79`；团队月聚合查询 `1534550261` 返回 `output_rows=88`、`income_all=26,962,143.26`、`refund_all=3,507,394.74`、折算后产出 `23,009,358.79`。个人、团队期、团队月 canonical 全量查询分别为 `1534559704`、`1534553633`、`1534556864`，均成功。
