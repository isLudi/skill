# Tiangong2 Python 任务诊断与端到端验收

## 目的与边界

本规范适用于“Tiangong2 Python 任务从数仓读取数据并写入外部承接系统”的故障诊断和交付验收。它约束 operator 如何读取证据、判断完成状态和停止后续动作，不赋予 operator 修改业务 Python、写入飞书、创建任务、调试、重跑或改变调度的权限。

业务 SQL、指标、渠道、期次、粒度和 Join 仍由对应领域 Skill 负责。operator 只允许对唯一 `query_sql` 执行 Hash 绑定的限定更新；如果修复涉及字段映射、OpenAPI 写入、回滚、批次或其他 Python 逻辑，operator 只能诊断和报告，不得保存完整候选源码。

具体任务 ID、Base/table/view ID、版本、行数、渠道数、阈值、失败节点 IP 和 Spark 参数都是运行期证据或任务配置，不能在本规范中固化为通用事实。

## 诊断顺序

### 1. 先固定身份和执行对象

开始读取日志前必须证明以下标识唯一且相互一致：

- 当前登录账号；
- project、数据开发一级目录、menu 和任务名；
- 任务负责人或创建人；
- Nezha task id、exec id 和 stage id；
- 当前源码 Hash、最新已发布源码 Hash 及执行所绑定版本。

任一标识不一致时停止。不得从同名任务、其他负责人目录或相邻执行实例拼接日志。

### 2. 读取完整日志而不是可见尾部

先用 `list-execution-history` 定位目标执行，再用 `fetch-execution-log` 读取全部 stage 和全部分页。分页位置必须单调推进且有上限；日志必须脱敏后写入 Tiangong2 专用 runtime。

诊断应沿异常链读取最深可靠的 `Caused by`、SQL 引擎错误码、Python traceback 或外部 API 返回码。Python2、SLF4J、cryptography 等 warning 只能记录为旁证，不能在没有因果证据时当作根因。

### 3. 按失败阶段分类

| 类别 | 可靠证据 | 处理方向 |
|---|---|---|
| 作用域或版本错误 | owner、menu、source/published Hash 或执行绑定不一致 | 停止；重新解析精确任务，不修 SQL、不执行 |
| SQL 解析或分析错误 | `AnalysisException`、字段/表/别名/类型/聚合错误及行列位置 | 把结构化错误交回原领域 Skill；禁止切域规避 |
| Spark/执行器错误 | 最深因果链中的 executor、shuffle、broadcast、节点或资源错误 | 记录精确签名和受影响执行；没有证据不得推断 OOM、超时或固定坏节点 |
| Python 运行错误 | Kyuubi 已结束后出现的 traceback、异常类型和源码位置 | 区分 query_sql 外源码问题；operator 不得借机扩大到完整源码保存 |
| 外部 OpenAPI 错误 | HTTP 状态、业务 code、批次位置、权限/字段/数据错误 | 区分认证、权限、结构、值域、限流和部分提交；响应正文必须脱敏 |
| 结果不确定 | 日志截断、分页异常、执行/stage 绑定不唯一或外部写入状态不可证 | 标记未验证并停止，不得用推测补齐 |

`BroadcastExchangeExec` 与 `SparkFatalException` 同时出现时，只能确认广播交换阶段发生 Spark 致命异常；除非日志另有直接证据，不得进一步宣称具体是 OOM、广播超限、超时或单一节点故障。

### 4. 禁止盲目重跑

读取失败日志不授权执行。相同源码和相同执行条件的失败不得自动重跑；已经存在的 exec 也不得调用“重跑”类接口。

只有完成根因分类、形成新的独立执行 Plan、确认当前源码等于最新已发布源码，并取得该次执行的显式授权后，才能调用一次 `execute-task-once`。执行请求不确定或已经发出时停止并要求人工核验，不能再次提交。

## 端到端验收门禁

平台终态成功不等于外部数据交付成功。验收范围由任务计划声明，并按以下门禁逐层证明。

### A. 发布与执行门

- 保存、提交、发布和执行分别存在独立 Plan/Receipt；
- 每个阶段的身份、任务、源码和计划 Hash 精确一致；
- 当前源码与最新已发布源码一致；
- 执行只产生一个新的 exec id，且未触发下游、未注入参数、未禁用 stage；
- task 和全部必需 stage 进入终态 success，进程 `exit_code=0`。

缺少任一回读时只能报告相应阶段“已请求但未完全验证”，不得向后推导成功。

### B. 查询结果门

任务日志必须输出可机器核验的查询完成标记，并证明计划要求的：

- 列集合或 schema Hash；
- 行数上下界；
- 分区、期次或其他快照一致性；
- 业务键唯一性；
- 必填字段、标记值域、数值边界和目标业务范围。

这些断言来自已审阅任务契约，不得把某次生产行数、固定期次或当前渠道清单写成 operator 的永久常量。

### C. 外部承接系统提交门

如果任务采用整表快照替换，日志至少应区分：

1. 写前目标和 schema 校验；
2. 新快照创建数量；
3. 新快照逐字段或等价 Hash 全量回读；
4. 仅在新快照验证后删除旧快照；
5. 最终记录集合、数量和关键不变量回读；
6. 新建或回读失败时只清理本批可识别新记录；
7. 请求不确定、旧记录删除失败或无法证明回滚时标记人工处理。

同周期数量骤降、记录上限、批次大小和回滚策略必须由任务计划配置并在任何外部写入前校验。operator 只核验日志和只读结果，不直接调用外部系统替任务写数据。

### D. 下游计算和展示门

当交付范围包含汇总、公式、视图或工作流时，还要只读证明：

- 原始键集合与汇总键集合符合预期；
- 加总字段与原始事实复算一致；
- 派生公式无错误且复算差异为零或处于计划容差内；
- 目标视图、过滤、分组和排序存在；
- 工作流身份、启用状态、触发条件和幂等行为符合计划。

如果用户指定数据必须由 Tiangong2 Python 写入，飞书 Skill 或 CLI 只能用于用户授权的只读结构核验和交付验收，不能代替任务写入。

### E. 完成状态

只有 A 至 D 中“本次交付范围要求的全部门禁”均有当前执行的精确证据，才可报告 `delivery_verified`。

其他常见状态必须如实区分：

- `platform_success_unverified_delivery`：平台成功，但外部全量回读不足；
- `failed_before_sink_mutation`：外部写入前失败，可确认未改变承接系统；
- `failed_after_sink_mutation_manual_attention`：写请求已发出但回读、删除或回滚不可证；
- `result_unresolved`：日志、分页、执行绑定或外部状态不足以得出结论。

不得把保存成功、发布成功、单个 SUCCESS 文本、抽样记录或页面可见数据单独当作端到端完成。

## 诊断与验收工件

工件只进入 Tiangong2 专用 runtime，至少记录：

- 精确任务和执行绑定；
- 当前/发布源码 Hash；
- stage 终态和日志 Hash；
- 最深可靠错误签名及其分类；
- 是否发生远端写请求；
- 各验收门的证据状态和缺口；
- 最终完成状态与人工处理要求。

不得保存凭据、Authorization、Cookie、默认参数块正文、完整业务载荷或未脱敏外部 API 响应。运行工件不会自动写入业务 Skill，也不构成保存、提交、发布或执行授权。
