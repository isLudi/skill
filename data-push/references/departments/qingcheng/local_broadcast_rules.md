## 图片视觉

- 整体视觉参考市场顾问部现有图片的深藏青表头、条件显示的总计行，以及固定指标色阶。现有市场 renderer 使用的 `#203b72` 深藏青和 `#b8c4d3` 浅蓝灰网格可作为青橙预览起点；最终样式由青橙自己的 renderer/style 持有并通过预览核对。
- 以下 **10 个指标**在对应图片中展示时，原则上配置色阶或进度条：**好友率、等待时长、8min、24h首call、综合人头转化率、综合单效、联报率、破蛋率、外呼时长、外呼频次**；渠道明确的较新要求优先，例如下文公海主管与顾问过程图只对其中四列画条。未出现在某渠道图片中的指标不为凑齐视觉效果而新增列。
- 色阶按指标使用固定档位或固定数值范围；进度条使用该指标固定的量程。相同指标的相同原始值在不同渠道、年级、群和时点应呈现相同视觉结果，不按当前图片行数、最大最小值或相对名次重新拉伸。数值本身仍清楚显示；空值和零分母遵循经确认的指标语义，不画成零值进度。
- 这项视觉授权不等于沿用市场顾问部的 `5min`、线索留存率、综合单效等阈值，也不确定青橙每个指标应选色阶还是进度条。实施前逐指标确认展示类型、单位、方向、档位或量程、上下界及异常值处理；尤其要区分 `8min` 的人数与比率、等待时长和外呼时长的统计窗口。
- 若后续确认显示总计行，使用与表头协调的深藏青样式；是否显示总计、总计包含哪些明细以及比率如何由分子分母重算，仍由各渠道业务口径决定。

## 同群同一时点逐渠道发送

- 同一目标群在同一业务时点涉及多个青橙渠道时，按显式配置的渠道顺序**逐渠道准备、生成并发送**该时点适用的报告。每个渠道形成自己的图片、消息和结果；不合并成一张跨渠道图片或一条混合消息。渠道顺序须在接入时固定，不能依赖 Base 行顺序或源数据返回顺序。
- 每个渠道独立做范围匹配、门槛、数据就绪、图片和提醒检查。仅当当期上游审计明确证明该渠道为零行时，记录 `skipped_no_eligible_rows`，不生成或发送空消息；其他有数据的渠道继续处理。审计缺失、源表与审计不一致或共享快照门禁失败属于错误，不能伪装成空渠道跳过。
- 回执和幂等键至少区分 `domain/local`、目标群 ID、渠道 ID、业务期次、报告类型及计划时点。每个渠道独立记录跳过、已发送、发送结果不确定和读回结果；一个渠道成功不代表同群其他渠道成功，重试也不能重复发送已成功的渠道。结果不确定时保留图片，并按"未确认送达的重发与只回读重验"一节分流：**收据没有 message_id 的用同一个幂等键重发（平台按同键去重，因此不是盲目重发）；已确认进群、有 message_id 的只补回读，绝不重发。**
- 单渠道的可隔离失败不应重发或抹掉其他渠道的成功回执；影响整批数据可信度的共享门禁失败则阻断受影响批次。发送前对同一时点的源版本和期次做一致性核验，避免串行投递期间混用不同快照。

## 未确认送达的重发与只回读重验（2026-09-29 起）

一次几秒的网络抖动曾经等于一条播报永久丢失。2026-09-29 12:20 `Codex-Lark-Qingcheng-SEC-Process-GroupPush` 的公域主管播报在取租户令牌时被对端重置连接，收据落成 `send_result_uncertain`；此后每一轮（任务计划程序每 2 分钟起一个新进程）都读到"需人工复核"而拒绝重试，空转到 `:50` 退出码 1，播报永久缺失。**重试机制本来就是为吸收这种抖动而存在的，却被自己的收据判据废掉了。**

判据已收窄为一条，由共享模块 `lark_delivery/common/resend.py` 的 `decide(status, message_id)` 提供：

> **有 message_id → 只补回读，绝不重发；没有 message_id → 用原键重发。**

- 重发安全的依据是**幂等键确定**：`_slot()` 把时间归一化到固定分钟、`second=0`，所以同一槽位每一轮算出的键逐字节相同。若那一条其实已进群，平台按同键去重并**返回原 message_id**，不会重复发；若没进群则补发。响应丢失那种真正模糊的情况也因此自愈——拿回原 message_id 后回读通过，槽位收敛。
- **不能按错误类型判断**：令牌可能是缓存的，刷新失败时发送照样可能已经出去，所以"错误发生在交付之前"不证明消息没发。只有幂等键能定这件事。
- 三个 runner（sec / special / partner）在 `_deliver` 里先按判据分流，再走原有的 `probe_revision` / `_verify_group` 前置校验；`reverify` 分支在探测之前返回，因为回读不依赖源，而源通常已经往前走（2026-09-29 当天 Base 从 rev 3263 走到 3264，探测会拦掉唯一不会重复发消息的那条路径）。
- `run_qingcheng_process.py` 走子进程发送：新增 `--reverify-only`（只读、无发送能力）供回读复用；子进程的收据守卫改为按判据放行——同一键在"已确认进群"时会被拒绝并要求改用回读。
- 若某级已有收据，`run()` 不再重新准备该级，直接交给投递循环处置；否则一次重发会去重取一个已经前进的源，把重试挡在门禁上。
- 收据新增 `resend_attempts` 与 `prior_status`：青橙每轮重写收据，运行日志只记最终结论，收据是唯一能看出"重发了几次、上一轮什么状态"的地方。

**发送前探测的传输失败轮内重试（2026-09-29 起）。** 四个 runner 的 `probe_revision`（发送前的 Base 版本探测）现在包在 `lark_delivery/common/retry.py` 的 `retry_transport` 里：探测**抛传输错误**（连接被重置等）时轮内重试 3 次、间隔 2 秒，仍失败才让该轮失败；探测**返回**了不同版本号则仍是结论，立刻 fail-closed、绝不重试。起因是 2026-09-29 16:20 的 SEC 槽位连续三轮倒在这次探测的连接重置上、整轮被白丢。

**内容不可回读的群（保密模式）。** 若目标群开了保密模式（`restricted_mode_setting.status=true` / `message_has_permission_setting="not_anyone"`），发送仍被允许但**消息内容读不到**，于是"message_id 取不到"变成结构性必然，而消息其实已经进群。这类群的回读失败记 `sent_unverifiable` 并**按可接受终态处理**（干净状态、不触发 `exit_code=1`），**且绝不换新键重发** —— 换了就会每轮补发一条。判定由 `lark_delivery/common/readback.py` 完成：配置声明优先，否则在回读失败路径上探测一次，探测失败一律判为可回读。2026-09-29 `⏰私域讨论`（Process 的 `private` 主管群）就是这种情况，当天实际收到播报却被判为失败。回读仍会重试，所以群里解除限制后会自动恢复 `sent_verified`。
